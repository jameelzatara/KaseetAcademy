# خطة تنفيذ الإصلاحات الأربعة الحرجة — كاسيت أكاديمي

> مبنية على تدقيق الكود الفعلي للموقع (أغسطس 2026). كل خطوة تشمل: الملفات المعنية، ماذا تفعل، وكيف تتحقق أنها نجحت.

## الإصلاح 1: نشر نسخة إنتاج (Production Build) على kaseet.com

### المشكلة الحالية
الموقع يعمل بوضع Vite التطويري — صفحة الـ HTML نفسها تحمّل:
`/@vite/client` و`/@react-refresh` و`/@replit/vite-plugin-dev-banner` وإضافة runtime-error.
هذا يعني: مئات الملفات غير المضغوطة، سكربتات HMR، وشريط Replit التطويري يظهر للزوار.

### الخطوات

1. **بناء نسخة الإنتاج**
   ```bash
   npm run build   # ينتج مجلد dist/ بملفات مضغوطة ومُجزّأة (code-split)
   ```

2. **تقديم الملفات الثابتة من الخادم**
   - في خادم Express (أو ما يعادله في مشروعك): قدّم `dist/` كملفات ثابتة، مع fallback إلى `index.html` لكل المسارات (SPA) — باستثناء `/api/*`.
   ```js
   app.use(express.static("dist"));
   app.get(/^\/(?!api\/).*/, (req, res) => res.sendFile("dist/index.html", { root: "." }));
   ```

3. **الضغط والتخزين المؤقت**
   - فعّل `compression` (gzip/brotli) على الخادم.
   - Cache headers: ملفات `assets/*.js|css` (بأسماء مجزّأة hashed) ← `max-age=31536000, immutable`، و`index.html` ← `no-cache`.

4. **النطاق والنشر على Replit**
   - انقل من " dev preview" إلى Deployment فعلي (Reserved VM أو Autoscale) على kaseet.com — صفحة Canonical وOG تشير لهذا النطاق أصلاً، لكنه لا يقدّم الموقع حالياً.
   - تأكد أن HTTPS مفعّل وأن `http://` يحوّل إلى `https://`.

### التحقق
```bash
curl -s https://kaseet.com/ | grep -c "@vite/client"   # يجب أن يعيد 0
curl -s https://kaseet.com/ | grep -c "dev-banner"      # يجب أن يعيد 0
```
ثم شغّل PageSpeed Insights — الهدف: LCP أقل من 2.5 ثانية على الجوال.

## الإصلاح 2: Prerender / SSR للسيو

### المشكلة الحالية
`curl` للصفحة الرئيسية يعيد `<title>` فقط وصفحة فارغة. كل الميتا (usePageMeta في `src/hooks/usePageMeta.ts`) تعمل بعد تنفيذ JavaScript — برامج الزحف ومعاينات واتساب/فيسبوك لا تراها. أنت تعتمد على البحث المجاني العربي، فهذا يكلّفك ترتيبك كله.

### الخيار الموصى به: Prerendering ثابت (وليس إعادة كتابة كاملة)
المحتوى شبه ثابت (صفحات دورات وتسويق)، فلا حاجة للانتقال إلى Next.js. استخدم `vite-plugin-prerender` أو `react-snap`:

1. **ثبّت الإضافة وعرّف كل المسارات** (من `src/App.tsx`):
   ```
   /, /courses/voiceover, /courses/voiceover-basics, /courses/voiceover-live,
   /courses/presenter, /courses/arabic-language, /courses/public-speaking,
   /masterclass-elam, /masterclass-voice, /masterclass-khataba,
   /voice-test, /privacy-policy, /terms, /refund-policy,
   /apply/voice-talent, /apply/trainer
   ```
   **استثناءات:** `/checkout`, `/checkout/success`, `/admin/orders` ← لا تُعرَّض مسبقاً وأضف لها `<meta name="robots" content="noindex">`.

2. **ميتا ثابتة لكل صفحة**: انقل قيم العنوان والوصف من `usePageMeta` إلى جدول route→meta يُحقن في HTML الثابت وقت البناء (title, description, canonical, og:title/og:description/og:image). احتفظ بـ `usePageMeta` للتحديث أثناء التنقل داخل التطبيق، لكن HTML الأولي يجب أن يحمل الميتا الصحيحة من أول بايت.

3. **بيانات Course المنظمة**: أضف JSON-LD من نوع `Course` (الاسم، الوصف، السعر، العملة، المدرّب، التوفر) في HTML كل صفحة دورة — يمنحك نتائج منسّقة في جوجل.

4. **حدّث sitemap.xml** بعد أي تغيير مسارات، وأرسله في Google Search Console.

### التحقق
```bash
curl -s https://kaseet.com/courses/voiceover | grep -o "<title>[^<]*"   # عنوان الدورة الحقيقي
```
ثم: أداة فحص URL في Search Console + مشاركة رابط في واتساب للتأكد من ظهور المعاينة.

## الإصلاح 3: التحقق من السعر والمقاعد في الخادم

### المشكلة الحالية (أخطر بند)
في `src/pages/CheckoutPage.tsx`:
- الأسعار ثابتة في المتصفح: `COURSE_PRICING`, `DEPOSIT_JOD = 50`, `FX_USD = 1.41`
- الطلب إلى `/api/checkout/session` **يرسل** `cohortCapacity`, `cohortEnrolled`, `cohortStartAr`… من المتصفح
أي زائر يستطيع تعديل الطلب بدقائق (DevTools) ليدفع أقل أو يتجاوز دفعة مكتملة — إذا كان الخادم يثق بهذه القيم.

### الخطوات

1. **مصدر حقيقة واحد في الخادم**: أنشئ `server/pricing.ts` (أو ما يعادله) يحوي الأسعار والعربون وسعر الصرف والخطط. احذف `COURSE_PRICING` من الواجهة — الواجهة تعرض فقط ما تجلبه من `GET /api/courses/:slug/pricing`.

2. **أعد كتابة `POST /api/checkout/session`** ليعمل هكذا بالترتيب:
   ```text
   أ) اقرأ cohortId فقط من الطلب — تجاهل كل حقول capacity/enrolled/price القادمة من العميل
   ب) اجلب الدفعة من قاعدة البيانات (وليس من JSON الواجهة)
   ج) تحقق: status == "open" والتاريخ لم يبدأ
   د) احسب المبلغ في الخادم من جدول الأسعار (courseSlug + mode + plan)
   هـ) داخل معاملة ذرّية (transaction): عدّ الحجوزات المدفوعة وقارن بالسعة؛
       إن اكتملت → أعد { error: "CAP_REACHED" } — وإلا أنشئ الحجز
   و) أرسل المبلغ المحسوب خادمياً فقط إلى بوابة الدفع
   ```

3. **انقل `cohorts.json` إلى قاعدة بيانات** (جدول cohorts: course, mode, status, start, capacity) مع واجهة تعديل في `/admin/orders`. هذا يحل أيضاً مشكلة "تحديث المواعيد يتطلب إعادة نشر".

4. **سجّل المبلغ المتوقع في الطلب** وقارنه مع webhook/تأكيد بوابة الدفع في `/api/checkout/status` — لا تعتمد "مدفوع" إلا بعد تطابق المبلغ والعملة.

### التحقق (اختبار تلاعب)
```bash
curl -X POST https://kaseet.com/api/checkout/session \
  -H "Content-Type: application/json" \
  -d '{"cohortId":137,"courseSlug":"voiceover","mode":"onsite","plan":"full",
       "cohortCapacity":999,"cohortEnrolled":0,
       "customer":{"firstName":"test","phone":"962770000000"}}'
```
النتيجة الصحيحة: جلسة دفع بالمبلغ الحقيقي الكامل من الخادم، وأي تعديل في الحقول لا أثر له.

## الإصلاح 4: التحليلات وأحداث التحويل

### المشكلة الحالية
لا يوجد أي تتبّع في الموقع كله: لا GA4، لا بكسلات، لا أحداث. القنوات التسويقية تعمل بلا قياس.

### الخطوات

1. **البنية التحتية** — أنشئ `src/lib/analytics.ts`:
   - يحمّل GA4 (gtag.js) + Meta Pixel + TikTok Pixel (حسب منصات إعلاناتك الفعلية)
   - يعرض دالة واحدة `track(eventName, params)` ترسل للكل
   - يحمّل البكسلات كسولاً (بعد تفاعل المستخدم الأول أو `requestIdleCallback`) حتى لا تضر بالأداء

2. **تتبع الصفحات في SPA**: اربط `page_view` بتنقّل wouter (useEffect على `useLocation`) — وإلا سجّلت كل الجلسة صفحة واحدة.

3. **خريطة الأحداث** (الاسم ← أين يُطلَق في الكود):

   | الحدث | المكان |
   |---|---|
   | `view_course` | صفحات `/courses/*` و`/masterclass-*` عند التحميل |
   | `begin_checkout` | `handlePay` في `CheckoutPage.tsx` قبل fetch |
   | `purchase` | `CheckoutSuccessPage.tsx` — **فقط بعد** تأكيد `/api/checkout/status` (مع value وcurrency وorder_id) |
   | `whatsapp_click` | مكوّن موحّد لكل روابط `wa.me` (يوجد 9+ روابط مبعثرة — وحّدها في مكوّن واحد يتتبع تلقائياً) |
   | `voice_test_submit` | نجاح إرسال اختبار الصوت |
   | `apply_submit` | نجاح `/api/apply/trainer` و`/api/apply/voice-talent` |

4. **تتبع المصدر (UTM)**:
   - عند أول زيارة: خزّن `utm_source/medium/campaign` في sessionStorage
   - أرسلها مع طلب checkout → الخادم يخزّنها في الطلب
   - النتيجة: لوحة `/admin/orders` تُظهر من أين جاء كل مشترٍ (غوغل؟ إنستغرام؟ إعلان مدفوع؟) — هذا أثمن رقم تسويقي ستملكه

5. **اختياري لاحقاً**: Meta Conversions API (حدث purchase من الخادم) لدقة أعلى مع حاجب الإعلانات.

### التحقق
- GA4 Realtime: نفّذ رحلة كاملة (دورة → دفع → نجاح) وتأكد من ظهور الأحداث الثلاثة بالترتيب
- Meta Events Manager: Test Events يُظهر `purchase` مع القيمة الصحيحة
